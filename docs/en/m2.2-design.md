# Outpost M2.2 design: weekly suggestions of new products

> 2026-11-28. The second M2 release (design §7.1 "weekly refresh", §10 M2 "weekly candidate refresh"). The user agreed to M2's order and said not to stop and wait, but to record the decisions and show them at the end. Everything below is my call.

## What the user sees

- Once a week, each track looks for new products by itself. What it finds shows under 「候选推荐 n 条待看」 (Suggestions, n waiting) below the track in the middle column (that row has been there since M1.2); opening it works as always: tick, then start following.
- The track page (M2.1) gets one more line in its header: "Weekly suggestions: on · last 11-26 · next 12-03", with a switch. Turned off, the track no longer suggests by itself; "Recommend another batch" under "+ Add a product" still works.
- The candidates page of a started track gets "None of these" at the bottom: the batch no longer counts as waiting.

## When

- After each day's brief and maps, every started track (not one still being picked) is looked at: if the switch is on, its last recommendation that **ran to its end** (the first one, a "Recommend another batch" or a weekly one) is 7 days old or older, and no recommendation is running, a recommendation starts.
- One skipped because the budget was spent, or one that failed, does not count as finished: it is tried again after the next day's brief. At most one try a day.
- A new track: 7 days from its first recommendation.

## What

- The usual recommendation session and prompt (§7.1), with one fixed "adjustment": a weekly refresh, hand in only products that appeared after the last batch or moved enough to be worth another look; nothing from the last batch that did not change; few qualify, few are handed in, none is fine.
- Products already in the track are not recommended again (the prompt already says so); those followed in another track are marked "already followed in … · only the missing dimensions" as before.
- The new batch replaces the previous one: old candidates not picked are no longer listed (they had a week).

## Cost

- About ¥0.5–1 per track per week (one recommendation session, like "Recommend another batch"), counted in that day's budget. Two tracks: about ¥1–2 a week.

## My calls

1. The switch is per track and on by default, on the track page, not in the global settings (the settings page is the Desktop's plugin configuration form, and a switch there means a new configuration option; per track is finer and easier to see).
2. The 7 days count from the last recommendation that finished; a "Recommend another batch" by hand moves the next one back too.
3. A skipped or failed one is tried again the next day, at most once a day.
4. No extra line in today's brief for new suggestions: the middle column's 「候选推荐 n 条待看」 already says so.
5. Version 0.2.2, tag m2.2.

## Changed after review (2026-11-28)

The independent review found nothing that blocks the release. Changed:

- **Products passed over no longer come back weeks later**: a recommendation used to remember only the batch before it, and a weekly batch is small, so in the third week the products not picked from the first batch would be offered as new. The recommendation session is now told "recommended before and not picked by the user" (up to 40), and leaves them out unless something new happened.
- **"n waiting" matches the page**: the count used to read "the latest batch with candidates" while the page shows "the latest recommendation"; when a recommendation was skipped, failed or found nothing new, the middle column still said to look, and the page was empty. Both read the same batch now.
- **"None of these"**: for a started track, the candidates page has a button at the bottom; the batch no longer counts as waiting, and the page goes back to the track. Before, only ticking and starting to follow counted as looked at, so a batch with nothing wanted kept the reminder up.
- **Tracks due on the same day run one after another**: they used to start together, with the budget checked only before each started, so together they could overshoot it; now each waits for the one before.
- **A round that did not run says why**: the track page's line reads "the last try did not run: why" (the budget spent, say).
- When today's daily run is through, "next" says tomorrow instead of today.
- The recommendation prompt now says that with an adjustment, the adjustment rules everything, including whether to hand in last round's products and how many (before, "hand in again what still fits" fought the weekly request).
- The weekly state is read with a query by track instead of reading every run each time.

Left: retrying a failed weekly recommendation from the Runs page runs an ordinary recommendation (a full batch), not "only new ones"; deleting a track while its weekly recommendation runs waits for it to finish.

## API and data

- `GET tracks/:id/overview` gains `weekly`: on or off, the last, the next, and whether one is running now.
- `POST tracks/:id/dismiss`: "None of these".
- `POST tracks/:id/weekly` (`{ on }`): on or off. Off is kept in the settings table (`weeklySuggestionsOff:<track>`) and deleted with the track.
- No new tables or columns; the database stays at version 5; going back to 0.2.1 is installing the older package.
- A weekly suggestion is an ordinary recommendation run (named "Suggest" on the Runs page) with the adjustment above.

## How it is checked

- Unit tests: the 7 days count from the last finished recommendation ("Recommend another batch" included, skipped and failed ones not); after a skip or failure it is tried the next day, at most once a day; nothing starts while a recommendation runs; none for a track turned off or still being picked; the switch's route; recommendations start only after the brief and the maps; the page's line, its switch and "See the new suggestions (n)".
- On the real Desktop: the switch clicked off and back on on the track page (free); a real weekly suggestion has to wait until a track's 7 days are up (both tracks first recommended on 11-26, so the first automatic one is the morning of 12-03).
