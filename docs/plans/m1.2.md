# 前哨 M1.2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 已有赛道能加产品（按名字加、再推荐一批），产品能在赛道间「移到 / 也加到 / 拿掉」。

**Architecture:** 宿主加一个很小的运行种类 `identify`（确认一个按名字加的产品，通过后自动走「开始跟踪」同一条路径），三个改产品所属赛道的接口复用 M1.1 的补卡路径；前端加「＋ 添加产品」页和「⋯」菜单里的三项。

**Tech Stack:** 同 M1 / M1.1。

**Spec:** `docs/m1.2-设计.md`；M1.1 `docs/m1.1-设计.md`；主设计 `docs/设计文档.md`。

## Global Constraints

- M1 与 M1.1 的全局约束全部照旧（`docs/plans/m1-core.md`、`docs/plans/m1.1.md` 的 Global Constraints；SDD 工作区副本 `.superpowers/sdd/m1.2/global-constraints.md`）。
- 新运行种类名 `identify`；提示词文件 `prompts/identify.md`，正文（去空白、去占位符）≤ 800 字；`identify` 和 `recommend` 一样不占「同时跑几个」的位置（`UNPOOLED`），但受预算限制。
- `identify` 交上来的候选不算一批推荐：`Repo.latestBatchId` 只看 `recommend` 运行产生的批次。
- 新接口：`POST tracks/:id/add-product` `{ name: string; officialUrl?: string }`、`POST products/:id/link` `{ trackId }`、`POST products/:id/unlink` `{ trackId }`、`POST products/:id/move` `{ from, to }`。都是 JSON（M1 的 415 规则）。
- 新文案逐字：「＋ 添加产品」「给「{track}」添加产品」「知道名字」「产品名」「如 Gemini Agent」「官网（可不填）」「加入并建档」「正在确认这个产品…」「已加入，正在建档」「没加进来：{reason}」「已在「{tracks}」跟踪，直接加进来了 · 只补缺的维度」「让前哨再找一轮」「一句话要求（可不填）」「再推荐一批」「约 ¥0.5、3–4 分钟」「正在找…」「去「候选推荐」看」「移到其他赛道…」「也加到其他赛道…」「从「{track}」拿掉」「还没有别的赛道」「已移到「{track}」」「已加到「{track}」」「 · 补 {count} 张卡」「这是它唯一的赛道。不想跟了就用「暂停跟踪」。」。

## Review Focus

1. **按名字加的正好是别的赛道已在跟踪的产品（写法略不同）** → 不跑确认、不花钱，直接加进来、只补缺的卡。测试在 Task 1。
2. **按名字加时推荐正在跑** → 不冲突：`identify` 单独跑，不顶掉、不打断那批推荐；它的结果不出现在「候选推荐」。测试在 Task 1。
3. **确认没通过（查无此产品 / 不属于这个赛道）** → 不建档、不加入，显示原因；花费照记。测试在 Task 1、Task 3。
4. **移走产品时它的日更正在跑** → 日更照跑完，哨报照常；新赛道的补卡等日更结束再做；不会同一产品同时两个核查。测试在 Task 2。
5. **拿掉最后一个赛道 / 移到已归档或自己已在的赛道** → 409，原样不动，菜单里显示原因。测试在 Task 2、Task 4。

**Interfaces:**
- Produces: `Repo.findFollowedByName(name: string): Product[]`——名字部分按 M1.1 的 `identityKey` 规则统一处理后相同、状态 tracking/paused/baselining 的产品（不看公司）。
- Produces: `startIdentify(deps: JobDeps, trackId: Id, ask: { name: string; officialUrl: string | null }): Promise<Id>`（返回运行 id）：提示词带赛道名、关注点、用户填的名字和官网、今天日期；Agent 只提交一个候选（tier `strong`/`consider` 表示通过，`excluded`＋reason 表示不通过）。运行结束后：有通过的候选 → 走与 `tracks/:id/start` 相同的「加入这个赛道」逻辑（含 M1.1 的 twin 处理、建档或补卡）；没有或 excluded → 运行 `done`，`error` 写 Agent 的 reason（没交候选时写「没有找到这个产品」）。
- Produces: `'POST tracks/:id/add-product': { body: { name: string; officialUrl?: string }; response: { linked: Id } | { runId: Id } }`——`findFollowedByName` 恰好一个 → 直接加入（不建运行）返回 `{ linked }`；否则开 `identify` 运行返回 `{ runId }`。名字空白 → 400；官网不是 http(s) 网址 → 400。

### Task 2: 产品在赛道间移到、也加到、拿掉（宿主）

**Files:**
- Modify: `src/host/api.ts`（三个接口）、`src/store/repo.ts`（`unlinkProduct(trackId, productId)`）
- Test: `tests/host/api.spec.ts`、`tests/store/repo.spec.ts`

**Interfaces:**
- Produces: `Repo.unlinkProduct(trackId: Id, productId: Id): void`。
- Produces: `'POST products/:id/link': { body: { trackId: Id }; response: { toppedUp: number } }`、`'POST products/:id/unlink': { body: { trackId: Id }; response: { ok: true } }`、`'POST products/:id/move': { body: { from: Id; to: Id }; response: { toppedUp: number } }`。`toppedUp`＝新赛道里它缺、要补的维度卡张数（0 时不补）。补卡走 M1.1 用的 `rt.scheduler.topUpNow`（它自己会等该产品正在跑的日更或建档）。
- 规则：目标赛道不存在 / 已归档 / 产品已在其中 → 409；`unlink` 或 `move` 会让产品没有任何赛道 → 409「这是它唯一的赛道。不想跟了就用「暂停跟踪」。」；`move` 的 `from` 不是它所在的赛道 → 409；`move` 在一个事务里先加后删。产品状态不变（暂停的移过去仍暂停）。

- [ ] **Step 1: 写失败的测试**（`api.spec.ts`）：`link adds the track and tops up only the missing cards`；`move swaps tracks in one step and reports the cards to fill`；`unlink refuses the last track`；`refuses an archived, unknown or already-joined target`；`move of a product whose daily run is in flight waits for it before topping up`（假调度器：`topUpNow` 被调用，且日更未被打断）；`a paused product stays paused after a move`。
- [ ] **Step 2: 运行，确认失败**
- [ ] **Step 3: 实现**
- [ ] **Step 4: 运行通过**，再 `pnpm check`。
- [ ] **Step 5: 提交** `feat(host): 产品可以移到、也加到、拿出赛道`
