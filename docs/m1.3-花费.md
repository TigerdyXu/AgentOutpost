# 前哨 M1.3 设计：花费记全

> 2026-11-27。用户让查「前哨记的花费对不对」，查出少记，用户同意修。查账的详细过程不在仓库里，结论写在这里。

## 为什么改

前哨显示的花费有三处不准：

1. **联网搜索没记。** 在 DeepSeek 线路上，每次 `web_search` 都是一次单独的模型调用（`deepseek-v4-flash`，发往 `api.deepseek.com/anthropic/v1/messages`）。DSH 拿到搜索结果后，就把这次调用的用量（`usage`）丢了；前哨只加主会话自己的回复。11-27 08:00 那一批一共搜了 191 次，估计少记 ¥0.8–5.4。
2. **一律按高峰价算。** 前哨所有花费都按高峰价估算，可 08:00 是闲时，实际只要半价，所以这部分多记了一倍。
3. **追问没记。** 追问会话的用量从来没有记下来，每次都显示 ¥0。

DeepSeek 的计费规则：自 2026-11-18 起，模型通过服务端工具做的搜索**不按次收费**，搜到的内容算作模型的输入 token。Flash 的价格是每百万 token 输入 ¥2、输出 ¥8、命中缓存 ¥0.04，闲时半价。高峰时段是工作日北京时间 9:00–12:00 和 14:00–18:00。

## 改了什么（我的判断，可改）

1. **搜索按次估算。** DSH 每发出一次搜索请求，就在会话里记一条 `web/deepseek-search-llm-request`，前哨数这些记录。每次搜索按约 8000 个输入 token、800 个输出 token 估算（`SEARCH_TOKENS`）。这是 2026-11-27 估出的范围（从 3000/300 到 20000/2000）的中间值。
2. **DeepSeek 线路按时段算价。**
   - 设置页的价格表仍然填高峰价，闲时自动按半价算；周末全天都算闲时。
   - 节假日认不出来，按工作日算。
   - 其他按量付费的提供方不打折。
   - 一次运行按它**开始的时刻**，整体算高峰或闲时；追问按每条回复的时刻算。
   - 不知道桌面版的默认模型是哪个时，按 DeepSeek 算，因为价格表本来就是 DeepSeek 的。
3. **追问记账。**
   - 每条回复、每次搜索的花费，都加到这个追问的运行记录上，并计入当天的花费和预算。
   - 预算不拦追问，因为追问是用户自己发起的。
   - 追问隔几天再接着聊，花费仍记在开始的那一天。
   - 按当前设置里的追问模型定价。
4. **运行记录里看得到搜索次数。** 鼠标停在花费上，会显示「含 n 次联网搜索，按每次约 8000 输入、800 输出 token 估算」。
5. **「再推荐一批」的提示改为「约 ¥0.5–1、3–4 分钟」。** 算上搜索，一轮推荐闲时约 ¥0.5，高峰约 ¥1。新建赛道页的每日估算是按最近日更的平均值算的，记全以后会自己跟上，不用改。

## 不做的

- **不改 DSH，也拿不到真实用量**，因为 DSH 把它丢了。要算得精确，有两条路：
  - 换成 DeepSeek 的 Search API：每次 ¥0.005，按次计费，次数就是真实的；
  - 等 DSH 把搜索的用量记下来。
- **不补算以前的运行记录。** 改之前的记录没有搜索次数，照旧显示原来的数。
- **还有几处小的少记或多记**（审阅时查出，影响都不大）：
  - 追问里如果开了子 Agent，子 Agent 的会话不算进去；
  - 调研模型不是 DeepSeek 时，搜索走 DeepSeek Search API（每次 ¥0.005），不会出现上面那条记录，所以不记；
  - 搜索请求发出后失败或被中断，也照样记一次；
  - 超过 30 天的追问再打开，接着聊的部分不记；
  - 一次搜索请求里，模型最多可以连搜 5 次，所以 `SEARCH_TOKENS` 是按「一次请求」估的。

## 以后校准

过几天拿 DeepSeek 的账单对一下。差得多，就调整 `SEARCH_TOKENS`（`src/core/cost.ts`）。
