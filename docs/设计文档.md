# 前哨（Outpost）设计文档

> DeepSeek Harness（下称 dsh）桌面版插件：选一个赛道，AI 推荐热点产品，你勾选后，Agent 每天自动调研、核查、更新档案，并给你一份「今日哨报」。
>
> 状态：**已定稿**（用户 2026-11-25 同意进入实施计划）。界面部分是用户在 2026-11-25 逐页挑定的；标「我的决定」的是 Claude 拍板、用户可改的。实施计划见 `docs/plans/`。

## 1. 为什么做

用户在持续跟进 Personal Agent 等方向的产品动态（Meta Muse、豆包·小豆、OpenAI Dots、Grok Bots、蚂蚁灵光……），之前是一次次临时让 Agent 去搜（例如 11-16 在飞书上让 dsh-superagent「看下最近 personal agent 有哪些新动态」）。临时搜的问题：每次从零开始、前后不连贯、看不出「变了什么」、结论真假难辨。

前哨要做的是**常驻的情报站**：每个产品有一份不断更新的档案，每天只报告新变化，每条结论都有出处、改动都留痕。

**给谁用**：用户本人自己跟进（不是给领导出报告）。所以优先「读得快、查得全、交互顺、界面好看」，不做汇报材料导出。

**参照物**：
- `~/Projects/RepoRadar`：同样的形状（建档 + 定期报告变化），对象是 GitHub 仓库。报告规范、变化追踪的思路可借鉴。
- `~/Projects/dsh-superagent/prototype/repo`（上游 commit 6337fc8）：一个能跑的第三方 dsh 插件包，前哨的工程骨架照它来。

## 2. 目标、非目标、反目标

**目标**
1. 选赛道 → AI 推荐候选（带热度证据和推荐理由）→ 勾选 → 自动建档。
2. 每天定时（默认 08:00）对每个跟踪中的产品做增量调研，经核查后更新档案，生成今日哨报。
3. 产品档案按「维度」组织（默认：定位、目标人群、价值场景、体验、关键技术、商业化；赛道可加自定义维度，如「记忆」），每个维度有结论、全文、出处、变化史。
4. 赛道页可横向对比（对比矩阵 + 定位地图），可发起跨产品的「专题」深挖。
5. 完全嵌在 dsh 桌面版里，看起来是 dsh 的一部分。

**非目标（这期不做）**
- 多人共享、团队协作、权限。
- 汇报材料（PPT / Word）导出。
- 手机端；系统通知推送（侧栏数字就是提醒）。
- 付费墙、需要登录才能看的内容。

**反目标（做出来也算失败）**
- 把没核实的东西写进档案；把 AI 的推论和事实混在一起。
- 为显得有内容而凑数。没动静就说没动静。
- 悄悄改结论不留痕。档案的每一处改动都要能查到「什么时候、因为哪条来源、改了什么」。
- 费用失控。

## 3. 约束

- **dsh 版本**：桌面版和源码都对齐到 **0.2.3-alpha.2**（用户 2026-11-25 定，当天已升级）。桌面版是 Electron，壳里跑的就是完整 Web 应用，插件界面在 Web 和桌面完全一样。注意：alpha.2 的桌面安装包是从官方下载站手动装的，更新渠道（nightly）目前只推 0.2.2-rc.5；更新程序设置为不降级（`apps/desktop/src/updates/electron-updater/channel.ts:12`），所以不会被拉回 rc.5。dsh 处于开发者预览，会有不兼容变更；`engines.dsh` 锁 `^0.2.3-alpha.2`，升级 dsh 后要回归一遍。
- **dsh 源码**：`/Users/tiger/workspace/DeepSeek/Harness/deepseek-harness`，master 在 `4b399c39a6`（tag `dsh-v0.2.3-alpha.2`）。下文 dsh 路径都相对它。superagent 锁的是 `^0.2.1-alpha.2` 和 `@deepseek-ai/cordis 4.0.5-alpha.1`，抄它的包配置时版本号要改成与 alpha.2 一致。以后升级 dsh，源码和桌面版要一起升。
- **升级前的备份**（2026-11-25）：`~/Projects/AgentOutpost-data/backup/` 里有升级前的 `~/.dsh`（不含运行时）、桌面版应用数据、rc.3 安装包（已核对校验值），可用于回滚。注意 `~/.dsh` 的备份里含 `.credentials.yaml`。
- **桌面版要开着才会跑**：dsh 的定时只在宿主运行时生效。笔记本合盖错过 08:00 的，在下次打开时补跑一次当天的（见 §7.6）。
- **联网**：本机所有外网走代理 `127.0.0.1:7897`。dsh 宿主启动时会把带代理策略的 undici 分发器装成全局默认（`packages/util/http-proxy/src/install.ts:234-238`），所以插件在宿主进程里直接用 Node 的 `fetch` 也走代理。`ctx.web.fetch` 只收 html / text / json / xml（`packages/web/web-fetch-http/src/policy.ts:78-84`），**下载图标这类二进制文件要用 Node `fetch`**，读网页正文用 `ctx.web.fetch`。（审阅后更正）
- **搜索能力**：dsh 自带的只有 DeepSeek 一家。在 deepseek 路由上用 DeepSeek Messages 搜索（不按次计费），其他情况用 DeepSeek Search API，抓网页用 HTTP fetch（`docs/subsystems/web.md` 的「Provider availability」一节）。`packages/web/web-search-exa`、`web-search-perplexity` 是空目录，并不存在。浏览器自动化（`ctx.browserUse`，Playwright MCP 等，`docs/subsystems/browser-use.md`）是实验功能，需在桌面版里手动开启；M1 的核查要用它，设置页和首次使用时要检查它是否可用，不可用时提示怎么开，并退回「打不开就待确认」。
- **dsh 代码规范**：插件 UI 只用 dsh 的 `--dsw-alias-*` 语义变量，不写颜色字面量，这样深色模式自动适配（`docs/web-styling.zh.md`）。仓库外的插件用不了 dsh 自己的 CSS Modules 构建预设，所以照 superagent：一个样式表以 `?raw` 文本导入、用 `<style>` 注入，类名统一加 `op-` 前缀（审阅后更正）。
- **Node**：dsh 0.2.3-alpha.2 源码要求 Node `^24.22.3`，本机开发前要先升级（当时是 24.14.1）；插件运行在桌面版自带的 Electron 44（Node 24）里，用 Node 自带的 `node:sqlite`。

## 4. 做法选择（Approaches）

| | 做法 | 取舍 | 结论 |
|---|---|---|---|
| 1 | **前哨自己当调度员**：插件后台自己定时，每个产品开一个 dsh 会话调研，Agent 用前哨的「交作业」工具提交结构化结论，另起核查，再汇总 | 工作量最大（规模和 superagent 相当）；换来界面需要的一切结构化数据、按产品隔离失败与费用、可并行 | **用户选定（2026-11-25）** |
| 2 | 借 dsh 自带「自动化任务」，每天往一个会话里发一句提示，一个 Agent 轮完所有产品 | 代码少；但串行慢、一错全停、质量全靠 Agent 自觉，建档进度 / 花费 / 变化史很难做可靠 | 不选 |
| 3 | 像 RepoRadar 那样独立程序，dsh 里只放入口 | 不符合「嵌进桌面版」；dsh 插件 UI 是页面内的 React 插槽，没有嵌外部网页的正式机制；重复造 dsh 已有的 Agent、搜索、模型 | 不选 |

## 5. 界面与交互（用户已定）

草图在 `docs/mockups/`（HTML 片段，浏览器直接打开；每页有两个方案，选中的见下）。图里的产品内容都是编的示例。

### 5.1 整体布局（`1-导航.html`，选 B）

- dsh 左侧栏多一行「🔭 前哨」（望远镜图标），有未读新动态时行尾显示数字（`sidebar.panellist.trailing`）。
- 点进去是 dsh 的整页主面板（`main` 插槽），面板内**两栏**：
  - **中栏**（约 244px，前哨自己的子菜单）从上到下：标题「前哨」＋「＋ 新赛道」按钮；**今日哨报**（右侧「n 条新」）；每个**赛道**一个可折叠分组，下面依次是「赛道概览 · 对比矩阵」、各产品（有新动态带蓝点）、「候选推荐（n 条待看）」；底部固定**运行记录**（右侧今日花费）和**设置**。
  - **右栏**：内容，**铺满剩下的宽度**（用户明确要求，不要居中窄栏）；需要多列的地方用自动换列的网格，屏幕越宽列越多。
- 选中态：浅蓝底＋蓝字＋加粗，不要左侧竖条。
- 不选的 A 方案（前哨再加一条自己的图标栏）会和 dsh 侧栏一起变成四栏，已否决。

### 5.2 今日哨报（`2-今日哨报.html`，选 A）

- 顶部：日期（「11月25日 · 周二」）、一行元信息（几点跑完、几个产品、几条值得看）、「‹ 昨天」翻页、「全部已读」。
- 一句话总结（浅蓝底块）。
- 赛道筛选胶囊：全部 n · 各赛道 n。
- **一条流，按重要程度排**，一张卡片一件事。卡片内容：产品图标和名称 · 赛道 · 重要程度标签（重要 / 值得留意）；一句话标题；「为什么值得注意」；来源胶囊；「改了档案：定位、商业化」；操作「看改动 →」「追问」。
- 小更新折叠成一行（「另有 2 条小更新，点开看」）；末尾一行「今天没动静：产品 A、产品 B」。
- 共用交互：
  - **看改动**：跳到该产品档案，滚到被改那张卡并展开，新加的字用浅蓝底。
  - **追问**：新开一个 dsh 会话，首条消息带上这条动态和该产品档案，然后在 dsh 里打开这个会话（会话名「追问 · <产品> <标题>」）。
  - **已读**：卡片滚出视野即算读过，变淡；侧栏数字随之减少，清零就不显示。
  - **待确认**：来源不够的标「待确认」，不写进档案（规则见 §8）。注意：草图里 OpenAI Dots「App Store 更新日志，只有 1 个来源，待确认」那张卡，按 §8 定稿后的规则应算已核实（应用商店更新日志是官方来源说自己的事），以本文为准。
  - 没动静的日子只有一行「今天没有值得看的变化」。

### 5.3 新建赛道（`3-新建赛道.html`，选 B：在右栏里原地进行）

- 点「＋ 新赛道」→ 中栏立刻出现这个赛道（状态「挑选中」，下面一项「挑产品 · 已选 n」），右栏变成挑选页。
- 顶部三步指示：① 说清关注什么 ② 挑产品 ③ 建档。
- 第 1 步只要：赛道名 + 一句话「关注什么」；六个默认维度已勾，可加自定义维度。确定后显示为一个摘要块（右侧「改」）。
- 第 2 步：AI 搜索候选（1～3 分钟）。**候选一个个冒出来**，不用等全部完成；可以离开页面，回来接着挑。
  - 状态行：「找到 14 个候选，按热度和贴合度排好 · 用时 2 分 10 秒」。
  - **一句话调整框**（「多找些国内的」「去掉硬件类」）：带着上一轮结果重新推荐。
  - 分组：**强烈推荐**（默认勾上，「全选这一组」）、**可以考虑**（不勾，卡片更紧凑）、**没推荐的 n 个及原因**（折叠）。
  - 候选卡片（网格铺满宽度）：图标、名称、公司 · 国内/海外 · 形态；一句话是什么；热度证据（迷你柱状图＋「找到 41 篇相关报道 · 热度上升」）；「为什么推荐」。选中＝蓝色描边＋右上角蓝勾。
  - 热度数字的含义要老实（我的决定，审阅后补）：dsh 的搜索不给总命中数，也不能按日期筛（`packages/web/web/src/types.ts:31-47`），所以只能是「Agent 实际找到的不重复报道数」，是下限而不是真实报道量，文案用「找到 n 篇」。柱状图按报道的发布日期分周统计，拿不到日期的不计入；能算出日期的不足 5 篇就不画柱状图，只写数字。
  - 吸底栏：「已选 5 个 · 预计每天 ¥x～y · 首次建档约 n 分钟，建好后明早出第一份哨报」＋「稍后再挑」＋「开始跟踪 5 个」。
- 第 3 步：中栏立即列出这些产品，各自显示「建档中」和进度，建好一个就能看一个。
- 赛道下的「候选推荐」每周自动刷新一次，有新冒头的放进去等你看。

### 5.4 产品档案（`4-产品档案.html`，选 A：结论卡片 + 原地展开）

- 对象头：产品图标（大）、名称、状态胶囊（跟踪中）、「公司 · 建档日期 · 最近更新时间」；右侧「全部展开」「⋯」「立即更新」（主按钮，近黑底白字，与 dsh 主按钮一致）。
- 页签：**档案｜动态（n）｜专题｜来源 n**。
- 档案页签：
  - **关键事实条**（一行等分格）：形态、平台、价格、首发时间、对标产品。
  - **一句话定位**（大一号加粗）。
  - **维度卡片网格**（宽屏 3 列，窄屏 2 列）：每张卡＝维度名（今天改过的带「今天改过」）＋2～3 条结论（可带 [n] 出处）＋「n 个来源」；右上「展开」。
  - **展开**：这张卡占满一整行，左侧（约 2/3）是全文（带出处编号）和来源胶囊，右侧（约 1/3）是「这一节怎么变过来的」时间线（日期＋一句话改了什么，最新的实心点）。「收起 ↑」。
- 动态页签：这个产品的所有发现，按时间倒序（与哨报卡片同样式，含已读和待确认的）。
- 来源页签：所有来源列表（标题、发布方、日期、类型、被哪些结论引用）。
- 共用细节：出处 [n] 悬停显示来源标题、日期和原文那一句，点击打开原网页；AI 推论挂橙色「推论」标签；新加的字浅蓝底保留 3 天后褪掉；自定义维度自动多一张卡。

### 5.5 赛道页（`5-赛道页.html`，选 A：定位地图 + 矩阵）

- 头部：赛道名，「跟踪 n 个 · 起始日期 · 每天几点 · 关注维度」；按钮「赛道设置」「＋ 新专题」。
- 一句话格局（浅蓝块，标「AI 归纳」）。
- 左半：**定位地图**。二维坐标，两条轴由 AI 按赛道提议（例：「寄生在已有 App 里 ↔ 独立 App / 系统级」「陪聊问答 ↔ 替你办事」），右上「换轴」可改。每个产品一个点（图标＋名称）；建档那天的位置画虚线空心圈，连线到现在的位置。地图整体属于推论。
- 右半：**专题**列表（标题、涉及产品、首版日期、一次性/每周更新、上次改了几处），最后一项是「＋ 写一个问题，AI 去深挖」。
- 下方：**对比矩阵**铺满宽度。列＝产品，行＝赛道的关注维度（每格是该产品那张卡的一句话版本），今天改过的格子浅蓝底＋「今天」；点格子跳到对应产品的那张卡。右上「导出表格」（导出 CSV 即可）。

### 5.6 专题

- 发起：一个问题＋选涉及的产品＋「一次性 / 每周更新」。
- 结果：结构同档案（结论卡片在前，展开看全文和出处）；每周更新的有「这一版改了什么」。
- 入口：赛道页列全部；产品页「专题」页签只列和该产品有关的。

### 5.7 运行记录与设置（未出草图，按同一套组件做，我的决定）

- **运行记录**：按天分组，每次运行一行（类型：推荐 / 建档 / 日更 / 核查 / 汇总 / 专题；对象；状态；用时；花费）；点一行在 dsh 里打开对应会话；失败的显示原因和「重试」。
- **设置**：每天几点跑（全局一个时间，所有赛道一起跑）；每日预算上限（总的、每个产品）；同时跑几个产品；各类任务用哪个模型；数据目录；是否开启浏览器兜底。插件管理页里的配置行（`plugins.row.config`）放同一份表单。

### 5.8 视觉规范

- 配色、字体、圆角、发丝线、阴影全部用 dsh 主题变量（我的决定，用户未反对）：白底、DeepSeek 蓝 `rgb(65,118,230)` 做强调、近黑正文、0.5px 发丝描边、主按钮近黑。深色模式随 dsh 自动切换。
- 字要大、要黑：正文 15px 起，阅读正文 15～17px，不用浅灰小字（用户在 RepoRadar 里多次反馈灰字小字费眼）。
- **产品图标**（用户要求）：能拿到官方图标（官网 favicon / 应用商店图标）就用官方的；拿不到的**统一一种颜色**（浅蓝底＋蓝色首字），不给每个产品随机配色。图标用 Node `fetch` 下载（见 §3），存到本地数据目录。
- 字少：卡片只放结论，细节靠展开。

## 6. 核心概念与数据

数据目录：插件配置项 `dataDir`，用户本机设为 `~/Projects/AgentOutpost-data`（我的决定：和 RepoRadar-data 一样放项目旁边，用户不喜欢项目散落在磁盘各处）。里面放一个 SQLite 数据库、图标文件、各次运行的原始材料。照 superagent 的 `Store`：单个 SQLite 文件，启动时加目录锁。不用 dsh 的 `storageDomain`，因为它每次把整块数据读进内存，档案越积越多会慢。

| 实体 | 主要字段 | 说明 |
|---|---|---|
| 赛道 Track | 名称、一句话关注点、维度列表、地图两轴、状态 | 维度默认 6 个，可加自定义。运行时间和预算是全局或按产品的，不挂在赛道上 |
| 产品 Product | 名称、公司、国内/海外、形态、图标路径、状态（候选 / 跟踪中 / 暂停 / 归档）、所属赛道（可多个）、每日预算上限（可选） | 同一产品可在多个赛道，但**只有一份档案**：维度＝所属各赛道维度的并集，档案卡按「产品＋维度」存，每天只跑一次（我的决定，审阅后补）。赛道页的花费＝它下面各产品花费之和（共享的产品在每个赛道都算进去） |
| 候选 Candidate | 赛道、产品、档次（强烈推荐 / 可以考虑 / 没推荐）、一句话、热度证据（报道数、趋势、近 5 周序列）、推荐或排除理由、批次 | 每次推荐或调整是一个批次 |
| 来源 Source | URL、标题、发布方、发布时间、抓取时间、类型（官方 / 媒体 / 用户评价 / 应用商店 / 社交）、是否该产品的官方来源、原文引句、核查时怎么打开的（普通抓取 / 浏览器 / 只有搜索摘要 / 打不开） | 引句用于悬停展示和核查 |
| 发现 Finding | 产品、运行、标题、为什么值得注意、重要程度（重要 / 值得留意 / 小更新）、来源列表、说的是「产品自己的事」还是「别人的说法」、核查状态（待核查 / 已核实 / 待确认 / 未证实 / 已撤回）、待确认的截止日期、影响的维度、是否推论、已读 | 哨报卡片就是发现 |
| 档案卡 Card | 产品、维度、版本号、一句话（给矩阵用）、2～3 条结论、全文（带 [n]）、来源、推论片段标记、本版新增片段、改动说明、时间 | **每次修改新增一个版本**，变化史就是版本列表 |
| 关键事实 Facts | 产品、形态、平台、价格、首发、对标；版本化 | |
| 地图位置 Position | 赛道、产品、日期、x、y、理由 | 建档时一份，之后每周一份 |
| 哨报 Brief | 日期、一句话总结、排好序的发现、小更新、没动静的产品、花费 | 每天一份（跨赛道） |
| 专题 Topic | 赛道、问题、产品、一次性/每周、版本（结构同档案卡） | |
| 运行 Run | 类型、对象、dsh 会话 id、状态、开始/结束、token、花费、错误 | 运行记录页的数据 |

## 7. 后台流程

所有调研都在 dsh 会话里进行，用前哨自定义的 agent 预设 `outpost-researcher`（在 `cordis.patch.yml` 里定义，照 superagent 的 `dsh-superagent-worker-preset`）：只带时间上下文、`web_search`、`web_fetch`、前哨工具（开启后再加浏览器工具），**不带** shell 和写文件工具。Agent 不写自由长文，所有产出都通过前哨工具提交：

| 工具 | 用途 |
|---|---|
| `outpost_read` | 读当前产品的档案、近 14 天的发现、已知来源（避免重复报告） |
| `outpost_submit_candidate` | 推荐时逐个提交候选，界面立即可见 |
| `outpost_submit_card` | 建档时提交一个维度的卡片 |
| `outpost_submit_facts` | 提交或修改关键事实 |
| `outpost_submit_finding` | 日更时提交一条发现（必须带来源和原文引句） |
| `outpost_propose_card_edit` | 提议修改某维度卡片（新文本＋依据的发现） |
| `outpost_done` | 本次运行结束，附一句总结 |

工具写法参照 superagent `src/app/tools/tool.ts`（zod schema＋execute）。参数校验失败时返回可读错误，让 Agent 自己改。

### 7.1 推荐（新建赛道、一句话调整、每周刷新）
一个会话「前哨 · 推荐 <赛道>」。输入：赛道关注点＋维度＋（调整时）上轮候选和调整要求。Agent 搜索后逐个 `submit_candidate`，最后提交「没推荐的」及理由。热度证据要可查（报道数来自搜索结果计数，趋势来自按周分桶），图标在提交候选时尝试获取。

### 7.2 建档
每个产品一个会话「前哨 · <产品> 建档」。逐维度调研，提交卡片和关键事实，然后进入核查（§7.4）。核查后的卡片写入第 1 版，并生成该产品在地图上的初始位置。

### 7.3 每日增量
默认每天 08:00（全局一个时间），每个跟踪中的产品一个会话「前哨 · <产品> 日更 <日期>」，最多同时跑 N 个（默认 3）。一个产品在几个赛道里都只跑一次。Agent 先 `outpost_read`，再只找「上次运行以来的新东西」（发版、更新日志、官方公告、报道、用户口碑），逐条 `submit_finding`，需要时 `propose_card_edit`。

### 7.4 核查
每条发现、每处卡片修改都要过核查。核查由独立的一次运行完成（单独会话或直接调模型，留给实现者定），规则见 §8，步骤：
1. **打开原文**：先用 `web_fetch` 普通抓取；打不开或内容是验证页 / 登录页的，用浏览器打开（`ctx.browserUse`，M1 就要有）；还打不开的，看搜索结果摘要里能否对上原话。
2. **对引句**：确认原文引句确实在页面（或摘要）里，并且支持这条结论。原文打开了但找不到引句、或引句不支持结论 → **已撤回**。
3. **数来源**：统计独立来源数（同一通稿被多家转载算一个），并判断有没有该产品的官方来源、说的是不是产品自己的事。
4. **不够就找**：按 §8 不够格、且只差一个第三方佐证的，核查 Agent 自己再搜一次（上限：每条发现最多 3 次搜索、打开 3 个网页），找到就补进来源。
5. **定状态**：已核实 / 待确认（来源不够，或原文打不开且摘要也对不上）/ 已撤回。

只有「已核实」的才进档案；「待确认」只出现在哨报和动态里（打不开的注明「原文打不开」）；「已撤回」不展示，但在运行记录里可查原因。

**待确认的后续**：之后 7 天，每天日更时顺带把这个产品的待确认发现再核一遍（只做第 4 步）。7 天内够格了就转正：写进档案，并作为「已证实」出现在当天哨报里。到期仍不够的标「未证实」，从动态里收起（可展开查看），不再提起。

### 7.5 合并与汇总
- 合并：已核实的卡片修改生成新版本，记录新增片段（用于浅蓝高亮）和改动说明（用于变化史）。
- 汇总（全部产品跑完，或到截止时间＝开始后 2 小时，默认 10:00；我的决定，审阅后补）：截止后才跑完的产品，结果补进当天哨报，卡片标「迟到」，侧栏数字随之增加；直接调模型（`ctx.llm.stream`，见 `packages/llm/llm/README.md`），生成一句话总结和发现的排序，折叠小更新，列出没动静的产品，写入当天的哨报。侧栏数字＝当天未读的「重要＋值得留意」条数。
- 每周：刷新候选、更新「每周」专题、更新地图位置、重算矩阵一句话。

### 7.6 定时与补跑
插件自己定时（在 `ctx.effect` 里用定时器，计算下一个本地 08:00），不用 dsh 的 schedule：它只能往会话里塞一句话，调不了插件自己的函数。宿主启动时若发现今天还没跑、且已过时间，立即补跑一次。正在跑时关掉桌面版的，下次启动时从未完成的产品继续（照 superagent 的 `assignmentInterrupted` 思路）。

### 7.7 追问
新建一个 dsh 会话（standard 预设，额外挂 `outpost_read`），首条消息放这条发现和产品档案摘要，然后用 `ctx.uiWorkspace.openSession(id)` 打开（照 superagent `src/client/index.tsx` 的 `openKnownSession`）。

### 7.8 费用与限额
- 按 usage 事件和价格表计算花费（价格表可在设置里改）。
- 每日总预算、每产品预算（可选）；超了就停掉剩下的产品，哨报里写明「因预算未跑：…」。
- 推荐页和设置页显示的「预计每天 ¥x～y」用最近 7 天的实际花费估算，没有历史时用保守默认值并标「估算」。

### 7.9 失败处理
- 网络或模型临时错误：照 superagent `src/executor/dsh.ts` 的 `transient()`，退避重试最多 3 次。
- 一个产品失败不影响其他产品；哨报里写「未能更新：产品 X（原因）」，运行记录可重试。
- 会话卡住（长时间无事件）：超时后取消，记为失败。

## 8. 可信度规则

1. 每条结论必须有来源和原文引句；没有的不收。
2. **什么算够格**（用户 2026-11-25 定）：
   - **官方说自己的事，一个来源就够**：发了什么功能、改了什么、价格、上线范围等，来源是该产品的官网、官方博客、官方公众号、应用商店更新日志或官方社交账号。界面上来源标「官方」。
   - **别人的说法，要两个独立来源**：用户量、评价、传闻、分析判断等，同一通稿的多家转载算一个。
   - 不够格的标「待确认」，不进档案，按 §7.4 补找佐证、7 天期限。
   - **原文打不开 ≠ 假**：普通抓取和浏览器都打不开的，搜索摘要能对上原话就算核实，否则按「待确认」，注明「原文打不开」。
3. AI 自己的归纳和判断（格局一句话、地图位置、「可能导流到电商」这类）一律标「推论 / AI 归纳」，不和事实混排。
4. 核查不过的整条撤回，运行记录里写明撤回原因。
5. 档案只追加版本，不覆盖；任何改动都能追溯到发现和来源。

## 9. 嵌进 dsh 的方式

照 superagent 的「前后两半」插件包（dsh 文档：`docs/user/develop/basic/publish.md`、`docs/subsystems/client-modules.md`、`docs/subsystems/slots.md`）：

- **包结构**：`package.json` 里 `"dsh": { "bundle": { "patch": "./cordis.patch.yml" }, "client": { "platform": "web", "inject": [...] }, "manifestVersion": 1 }`，`exports["./client"]` 指向前端包。inject 列表照抄 superagent。
- **后台一半**：Cordis 插件，`apply(ctx, config)`；配置用 Schemastery（`dataDir` 必填，其余见 §5.7）。
- **后台接口**：`ctx.webServer.register({ kind: 'prefix', path: '/outpost', ... })`，挂在 `/outpost/api/*`。alpha.2 的路由有 `auth` 选项（`anonymous` / `required` / `deny`，默认 `required`，见 `docs/subsystems/web-server.md:53`），用默认的 `required` 交给宿主做认证；superagent 自己做的回环地址和同源检查（`src/app/http.ts:231-237`）可以保留作为第二道防线。前端轮询拿数据（照 superagent `src/client/api.ts` 的 `usePoll`）；有运行进行时轮询加快（如 2 秒），保证候选和建档进度能一个个冒出来。
- **前端一半**：`ctx.slots` 注册 `main`（key `outpost`）、`sidebar.panellist`（id `outpost`，标签「前哨」，望远镜图标）、`sidebar.panellist.trailing`（未读数）、`plugins.row.config`（设置表单）。面板内的中栏和右栏是前哨自己的 React 组件，面板内路由由前哨自己管。
- **预设**：`cordis.patch.yml` 里插入前哨插件本身和 `outpost-researcher` 预设（§7）。
- **构建**：前端包必须是 dsh 要求的 lazy-CJS `factory(require)` 格式，dsh 的构建预设没有发布，照抄 superagent 的 `tsdown.config.ts`；外部依赖只能用 dsh 平台模块表里的（`packages/client/modules/README.md`）。
- **开发期**：用单独的 dsh 目录（如 `~/.dsh-outpost`）跑网页版调试，不碰桌面版的 `~/.dsh`（superagent 用 `~/.dsh-superagent` 也是这个原因）。
- **安装到桌面版**：用桌面版自带的 `dsh` 命令或应用内「插件」页 `dsh plugin add ~/Projects/AgentOutpost`，重启后侧栏出现「前哨」。
